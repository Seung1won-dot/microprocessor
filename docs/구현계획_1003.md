## 1. 프로젝트 개요

학생회관 식당에 **카메라 3대**를 설치하고, **라즈베리파이 5**가 2~10분마다 사람 수와 테이블 점유를 추론해 혼잡도까지 계산한 뒤 서버로 보낸다. 학생은 복도의 QR 코드를 찍어 현재 혼잡도와 예상 혼잡도를 폰으로 확인한다.

- **목표**: 식당에 가기 전에 혼잡한지 미리 알 수 있게 하기
- **핵심 아이디어**: 파이가 추론과 혼잡도 계산까지 하고, 서버에는 영상이 아니라 **결과만** 보낸다 (엣지 컴퓨팅)
- **결과물**: 모바일 혼잡도 웹 — 여유/보통/혼잡 + 예상 대기 시간 · 추천 시간 · 오늘 시간대별 실측·예측 그래프

## 2. 시스템 구성도

```
[식당 내부]  카메라 3대 ──Wi-Fi──▶ 라즈베리파이 5 (핫스팟 · 추론 · 혼잡도 계산) ──▶ 노트북 (서버 · DB · 웹)
[인터넷]     노트북 ──핸드폰 USB 테더링──▶ 터널 / 학교 도메인 ──▶ 학생 폰 (QR)
```

카메라 → 파이 → 노트북은 **파이 핫스팟 안에서** 연결되고, 노트북만 테더링으로 인터넷에 나간다.

## 4. 네트워크 구성

라즈베리파이 5 내장 와이파이로 핫스팟을 만들어 카메라와 노트북을 연결한다. 인터넷은 노트북만 핸드폰 USB 테더링으로 연결한다.

**학교 와이파이를 쓰지 않는 이유**
- 학번/생년월일 로그인 방식(웹 로그인 또는 WPA2-Enterprise)을 Tapo 카메라가 지원하지 않는다.
- 학교 와이파이는 보통 기기끼리 통신을 막아서(클라이언트 격리) 파이가 카메라 영상을 못 받을 수 있다.

| 기기 | 연결 | 비고 |
|---|---|---|
| 라즈베리파이 | 내장 와이파이로 핫스팟 생성 (2.4GHz, WPA2) | 카메라 1대 바로 옆, 높은 곳에 설치 |
| 카메라 3대 | 파이 핫스팟에 접속 | 2대는 다른 위치(가장 먼 곳 약 15m, 벽 없음), 1대는 파이 바로 옆 |
| 노트북 | 파이 핫스팟 + 핸드폰 USB 테더링 | 테더링으로 외부 공개 |

**핫스팟 설정** (Raspberry Pi OS Bookworm, NetworkManager 기본 내장)

```bash
sudo raspi-config   # Localisation → WLAN Country → KR (설정 전에는 와이파이가 꺼져 있음)
sudo nmcli con add type wifi ifname wlan0 mode ap con-name capstone-ap ssid CapstoneCam autoconnect yes
sudo nmcli con modify capstone-ap \
  802-11-wireless.band bg 802-11-wireless.channel 6 \
  wifi-sec.key-mgmt wpa-psk wifi-sec.proto rsn wifi-sec.pairwise ccmp \
  wifi-sec.psk "비밀번호8자이상" \
  ipv4.method shared ipv4.addresses <내부 주소>/24
sudo nmcli con up capstone-ap
```

**카메라 등록**
1. 핸드폰을 `CapstoneCam`에 연결하고 Tapo 앱으로 카메라 3대를 등록한다.
2. 등록 마지막에 실패하면, 핸드폰 USB 테더링으로 파이에 잠깐 인터넷을 연결하고 다시 한다.
3. 앱의 고급 설정에서 카메라 계정(RTSP용 아이디/비밀번호)을 만든다.
4. 파이에서 `cat /var/lib/NetworkManager/dnsmasq-wlan0.leases`로 카메라 IP를 확인한다.

**범위 확인**: 파이 내장 와이파이는 트인 공간 기준 약 10~20m가 안정 범위. 실제 위치에서 `iw dev wlan0 station dump`로 신호가 -70dBm보다 좋은지 확인하고, 점심시간에도 `ping`으로 끊김을 확인한다.

## 5. 라즈베리파이: 캡처 → 추론 → 혼잡도 계산 → 전송

점심시간에는 2분, 나머지 시간에는 5~10분마다 카메라 3대에서 프레임 몇 장만 꺼내 추론하고 혼잡도까지 직접 계산한다. 영상을 계속 분석하지 않아 발열과 네트워크 부담이 작다.

| 시간대 | 주기 | 이유 |
|---|---|---|
| 11:00~13:00 | 2분 | 사람이 가장 많고 혼잡도가 빨리 변함 |
| 그 외 운영 시간 | 5~10분 | 변화가 적고, 발열도 줄어듦 |

1. **프레임 캡처** — 주기마다 OpenCV로 RTSP 스트림에 접속해 프레임 몇 장만 읽고 연결을 닫는다. 주소: `rtsp://계정:비번@카메라IP:554/stream1`(1080p) 또는 `/stream2`(저화질)
2. **사람 검출** — YOLO11n(또는 YOLOv8n)을 NCNN 형식으로 변환해 CPU로 실행. 한 장에 약 0.2~0.5초. `person` 클래스만 세고, 몇 초 간격 3~5장의 **중앙값**을 써서 순간 가림 오차를 줄인다.
3. **테이블 점유 판단** — 카메라가 고정이므로 처음에 테이블(좌석) 영역을 한 번 지정. 검출된 사람이 테이블 영역 안에 있으면 "점유".
4. **중복 제거** — 카메라마다 담당 구역(ROI)을 정해 겹치는 영역을 두 번 세지 않는다.
5. **혼잡도 계산** — 3대의 결과를 합쳐 좌석 점유율과 대기 인원으로 여유/보통/혼잡을 정한다 (7절).
6. **전송** — 계산 결과(JSON)만 HTTP POST로 서버에 보낸다. 사람 수와 점유 테이블 수도 함께 보내 기준 조정·예측 학습에 쓴다.
7. **자동 실행** — systemd 서비스로 등록해 부팅 시 자동 시작, 오류 시 재실행.

```json
{ "people": 41, "occupied_tables": 14, "total_tables": 30, "waiting": 5,
  "level": "보통", "timestamp": "2026-10-07T12:05:00" }
```

**예외 처리**: 카메라 접속 실패 → 그 카메라는 건너뛰고 다음 주기에 재시도. 서버 전송 실패 → 파이에 임시 저장 후 나중에 전송.

**테스트용 영상 저장**: 테스트 날에만 파이에서 `ffmpeg -c copy`로 재인코딩 없이 녹화, 필요할 때 Tailscale로 노트북에 가져온다. 평소 운영 중에는 영상을 저장하지도 보내지도 않는다.

### 고려 중인 대안: 카메라당 15fps 영상 송신

| 항목 | A. 프레임 캡처 (기본) | B. 15fps 영상 송신 (대안) |
|---|---|---|
| 동작 | 2~10분마다 RTSP에 접속해 3~5장만 가져옴 | 카메라 3대가 15fps 영상을 파이로 계속 보냄 |
| 파이 부하·발열 | 낮음 (주기마다 몇 초만 일함) | 높음 (영상 3개를 계속 디코딩) |
| 와이파이 | 잠깐만 사용 | 영상 3개가 핫스팟을 계속 사용, 끊김 위험 증가 |
| 정확도 | 순간 가림에 약함 (중앙값으로 보완) | 여러 프레임을 이어 볼 수 있어 가림·잠깐 자리 비움에 강함 |
| 추가로 알 수 있는 것 | 그 시각의 사람 수·테이블 점유 | 출입 인원, 줄 길이 변화, 테이블 점유 시간 |

**B의 핵심 문제**: 파이 5 CPU로 YOLO는 한 장에 약 0.2~0.5초 → 초당 약 2~5장. 3대 × 15fps = 초당 45장은 불가능.
B를 쓴다면 영상은 15fps로 받되 추론은 카메라당 초당 1장 정도로 스킵하고, 저화질 스트림(`/stream2`)을 쓰며, 더 필요하면 AI 가속기(AI HAT) 추가를 검토한다.

**결정 방법**: A로 먼저 구현하고, 책상 테스트에서 B도 돌려 본다. 파이 온도 · 초당 추론 수 · 핫스팟 끊김 · 사람이 직접 센 값 대비 오차를 비교해 최종 방식을 정한다.

## 6. 서버 · 웹 · QR 공개

서버와 웹을 띄우는 방식은 **아직 미정.** 파이가 보낸 결과를 서버가 저장·예측해 웹에 보여 주는 흐름만 정해져 있다.

| 구성 요소 | 기술 (예시) | 역할 |
|---|---|---|
| API 서버 | FastAPI (Python) | 파이 결과 수신 `POST /api/counts`, 혼잡도 제공 `GET /api/status` |
| DB | SQLite | 혼잡도·사람 수·점유 테이블 수와 시각 저장, 예측용 데이터 누적 |
| 웹 페이지 | HTML + JS (모바일 우선) | 현재 혼잡도, 시간대별 그래프, 30초마다 자동 갱신 |
| 외부 공개 | Cloudflare Tunnel 또는 ngrok | 노트북 서버를 인터넷 주소로 열기 |
| 도메인 | 학교 제공 | 터널 주소에 연결 (전산팀에 CNAME 요청) |
| QR 코드 | 도메인 주소로 생성 | 복도에 부착 |

**웹 화면 구성 (모바일 한 화면, 3개 영역)**
1. **지금 상태 한 줄** — 인원수·퍼센트 대신 "여유/보통/혼잡" 3단계와 예상 대기 시간(분). 갱신 시각과 센서 상태를 함께 표시하고, 센서가 끊기면 "실측 없음, 예측값"으로 바꿔 보여 준다.
2. **추천 시간** — "12:45 이후 여유 예상"처럼 예측을 행동으로 바꿔 준다.
3. **오늘 시간대별 그래프** — 지난 시간은 실측(채운 막대), 남은 시간은 예측(점선 막대). 여유가 되면 예측을 범위(밴드)로.

**학교 도메인 연결 방식**
- 도메인만 제공하는 경우: 전산팀에 "이 도메인을 터널 주소로 CNAME 연결해 줄 수 있나요?" 요청
- 서버(호스팅)까지 제공하는 경우: 웹 서버를 학교 서버에 올리고, 노트북은 파이 데이터를 넘겨주는 중계만

**운영 주의**: 노트북 절전 모드·화면 꺼짐을 끄고 충전기를 꽂아 둔다. 노트북이 잠들면 웹도 멈춘다.

## 7. 혼잡도 계산과 예측

현재 혼잡도는 파이가 좌석 점유율과 대기 인원으로 계산하고, 예측은 서버가 쌓인 데이터로 **30분 뒤** 혼잡도를 추정한다. 주제명이 "예측"이라 예측 기능이 꼭 필요하다.

**좌석 점유율(%) = 점유된 테이블 수 ÷ 전체 테이블 수 × 100**

| 단계 | 기준 (예시, 조정 가능) |
|---|---|
| 여유 | 40% 미만 |
| 보통 | 40~70% |
| 혼잡 | 70% 이상 |

학생이 궁금한 건 "몇 명 있나"보다 "앉을 자리가 있나"이므로 좌석 점유율로 단계를 정하고, 줄 선 사람(대기 인원)이 많으면 한 단계 올린다.
**한계**: 가방·식판만 두고 자리를 비운 테이블은 빈 자리로 잡힐 수 있다. 처음엔 사람 유무로 판단하고, 필요하면 가방·컵 같은 물체 검출을 추가한다.

**예측 방법 (단계적으로 발전)**
1. 1단계 — 평균 기반: 요일·시간대(10분 단위)별 평균 사람 수. 데이터 1~2주만 있어도 동작
2. 2단계 — 머신러닝: 요일 · 시각 · 최근 10~30분 사람 수 · 학사일정(시험기간 등)을 입력으로 회귀 모델(랜덤포레스트, LightGBM) 학습
3. 평가: 예측값과 실측값의 오차(MAE)를 비교해 보고서에 넣는다

**웹에 내보내는 예측 결과**: 예상 대기 시간(분), 추천 시간, 남은 시간대의 예측값과 범위. **예상 대기 시간 계산 방법은 아직 미정.**

**검출 정확도 검증**: 무작위 사진 몇십 장을 사람이 직접 세서 YOLO 결과와 비교. 사람이 많이 겹치는 점심시간 사진을 꼭 포함. 테이블 점유 판단도 같은 방식으로 비교.

## 8. 설치 허가와 영상 관리

**설치 허가는 받았다.** 평소에는 계산 결과만 서버로 보내고, 영상은 테스트 날에만 저장해 학교 측과 공유한다.

| 구분 | 영상 저장 | 노트북으로 보내는 것 |
|---|---|---|
| 평소 운영 | 안 함 (프레임은 추론 후 바로 삭제) | 파이가 계산한 혼잡도·사람 수 (JSON) |
| 테스트 날 | 파이에 녹화 | 사람 수 + 필요할 때만 Tailscale로 영상 파일 |

- [x] 학교와 식당 운영 측 설치 허가
- [ ] 식당 입구에 촬영 안내문 부착 (목적, 촬영 범위, 관리 책임자, 연락처)
- [ ] 테스트 영상의 보관 기간과 공유 방법을 학교 측과 정하기
- [ ] Tapo 클라우드 녹화 끄기, 카메라 계정과 핫스팟 비밀번호 강하게 설정

**Tailscale로 영상 가져오기**
1. 파이와 노트북에 Tailscale을 설치하고 같은 계정으로 로그인
2. 노트북에서 `scp pi@파이이름:/녹화경로/파일.mp4 .`
3. 파이는 핫스팟 때문에 평소 인터넷이 없으므로, Tailscale을 쓸 때는 핸드폰 USB 테더링으로 잠깐 연결. 노트북이 파이 핫스팟에 접속해 있으면 Tailscale 없이 `scp`로 바로 가져올 수도 있다.

> **보고서·발표 포인트**: "라즈베리파이가 추론과 혼잡도 계산까지 직접 하고, 서버에는 영상이 아니라 결과만 보낸다"는 엣지 컴퓨팅 구조를 강조한다.

## 9. 진행 순서

연결 문제를 가장 먼저 확인하고, 데이터는 최대한 일찍 쌓기 시작해야 예측 모델을 학습할 수 있다. 날짜는 팀 일정에 맞게 채운다.

1. **준비** — ~~재료비 승인~~ **재료비 구매 완료(10/7)**, 식당 좌석 수와 카메라 위치 조사
2. **책상 테스트** — 파이 OS 설치, 핫스팟 설정, 카메라 등록, RTSP로 사진 가져오기, YOLO로 사람 세기·테이블 점유 판단, A/B 방식 비교
3. **현장 테스트** — 실제 설치 위치에서 신호 세기(`iw`, `ping`)와 화각 확인, 점심시간에도 확인
4. **서버 개발** — 서버·웹 방식 결정, 파이 → 서버 전송 연결
5. **설치 + 데이터 수집** — 카메라와 파이 설치, 케이블 몰딩 정리, 매일 자동 수집 시작
6. **웹 개발** — 지금 상태 한 줄, 추천 시간, 오늘 시간대별 실측·예측 그래프
7. **예측** — 평균 기반 → 데이터가 쌓이면 머신러닝 모델로 발전
8. **외부 공개** — 터널 + 학교 도메인 연결, QR 제작, LTE 폰으로 접속 테스트
9. **시연 준비** — 복도 QR 부착, 전날 리허설, 정확도·예측 오차 정리

## 10. 위험 요소와 대응

| 위험 | 원인 | 증상 | 대응 |
|---|---|---|---|
| 핫스팟 범위 부족 | 파이 내장 안테나는 트인 공간에서 약 10~20m, 가장 먼 카메라는 약 15m. 사람 몸이 2.4GHz를 흡수 | 먼 카메라가 끊김, 특히 점심시간 | 파이를 먼 카메라 2대까지 거리가 짧아지는 높은 곳에, **금속 케이스는 신호를 가릴 수 있음 — 10/7 구매한 알루미늄 케이스를 씌운 채로 측정**(3절 참고), 현장에서 `iw`로 -70dBm 이상 확인, 점심시간 `ping` 확인 |

| 검출 오차 | 사람끼리 겹치거나 멀면 YOLO가 놓침. 카메라 겹침 구역 이중 계수. 짐만 두고 자리 비우면 빈 테이블로 잡힘 | 혼잡할수록 사람 수를 적게 셈 | 카메라를 높이 달아 내려다보게, 카메라별 ROI 분할, 3~5장 중앙값, 테이블 점유 병행, 테스트 영상으로 사람이 센 값과 비교해 보정 |
