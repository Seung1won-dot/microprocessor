## 1. 최종 주제

> ### 교내 식당 대기시간 예측·안내 시스템
>
> 배식구 통과 인원으로 **처리율**을, 카메라로 **대기 인원**을 실시간 측정하여
> **"지금 줄 서면 몇 분"** 을 산출하고, 식당 입구 **신호등**으로 표시한다.
> 나아가 **"5분 뒤 도착 시 예상 대기시간"** 을 예측하고 **식당 간·코너 간 비교**를 제공하여 수요를 분산시킨다.

### 핵심 공식

```
대기시간  =  대기 인원  ÷  배식 처리율
             (카메라·AI)    (빔브레이크 인터럽트, 실시간 계측)
```

## 2. 왜 이 주제인가 — 검토 과정

9/3 회의에서 나온 두 후보(셔틀버스 / 학생식당)를 놓고 아래 순서로 검토했습니다.
**이 과정에서 나온 반론이 모두 설계 근거가 되었으므로, 제안서 "설계 근거" 항목에 그대로 사용합니다.**

### 2-1. 처음에는 셔틀버스가 유력했습니다

식당의 초기 구상은 출력이 *"지금 혼잡합니다"* 였는데, **학생이 그 정보로 할 수 있는 행동이 없었습니다.**
반면 셔틀은 *"이번 차 탑승 불가 → 다음 차 14분 뒤 → 걸어가면 11분"* 이라 행동이 바뀝니다.

### 2-2. 셔틀에 제기된 반론 4가지와 그 해결

| # | 반론 | 검토 결과 |
|---|---|---|
| 1 | 교내 순환 · 신창역 등 **노선이 여러 개** | 신창역 노선만 중간 하차가 없어 출발지 카운트로 차내 인원 확정 가능 → **1개소로 범위 축소** |
| 2 | 셔틀이 **여러 대**, 차종도 섞임 | 사람이 암산 불가 → 오히려 시스템이 필요한 이유가 됨. **차종 분류 AI 추가** |
| 3 | **입석**이 있어 정원이 고정이 아님 | 정원은 상수가 아니라 **분포** → 뺄셈으로 안 풀림 → 진짜 AI 필요. 출력을 **3구간 확률**로 변경 |
| 4 | 사람 많으면 **2대로 증차** 운영 | 증차는 도착 전에만 불확실 → 무게중심을 **예측 → 실시간 계측**으로 이동 |

**네 반론 모두 해결되었고, 셔틀도 실행 가능한 주제입니다.**
다만 이 과정에서 셔틀의 구조적 약점이 함께 드러났습니다.

### 2-3. 그럼에도 식당으로 결정한 이유

| | 셔틀 | **식당** |
|---|---|---|
| **데이터 축적 속도** | 학기 내내 모아도 "만차 배차" 레이블 수십 건 | **점심 1시간에 수백 명 통과** — 하루가 셔틀 한 달치 |
| 설치 환경 | 실외 (방수 하우징 · 전원 · 조명 · 날씨) | **실내** (전원 있음, 조명 일정, 인식률 안정) |
| 불확실성 원천 | 증차 · 입석 · 차종 · 배차 간격 (4개) | **배식 처리율 1개** (그마저 실시간 계측됨) |
| 데이터 수집 난이도 | 정류장에 일부러 가서 배차 대기 | **팀원이 밥 먹으러 가면서 수집** |
| 2인 팀 적합성 | 보통 | **높음** |

> 결정적 이유는 **데이터 축적 속도**입니다.
> 셔틀의 최대 리스크는 "학기말에 학습할 데이터가 없을 수 있다"였고, 이는 **팀이 통제할 수 없는 변수**였습니다.
> 식당은 이 리스크가 사라지면서, 셔틀 검토에서 만든 설계는 **거의 그대로 이식**됩니다.

### 2-4. 셔틀 설계가 식당으로 이식되는 대응 관계

| 셔틀 버전 | 식당 버전 |
|---|---|
| 대기줄 인원 검출 (카메라) | 동일 |
| 빔브레이크 인터럽트 = 승차 카운트 | **배식구 통과 카운트** (통과 0.3초, 인터럽트 필요성 동일) |
| **실효 정원** (입석 때문에 분포) | **배식 처리율** (메뉴·인력 따라 분포) |
| 탑승 확률 3구간 (녹/황/적) | **대기시간 3구간** |
| 계측 모드 / 예측 모드 2단 구조 | 그대로 |
| LED 커트라인 + 서보 안내판 | 입구 신호등 + 서보 안내판 |
| 폴백: 애매하면 "탑승 가능"을 띄우지 않음 | 폴백: 애매하면 **대기시간을 길게** 표시 |

> 셔틀은 제안서 **"확장 가능성"** 항목에 2줄로 남깁니다.
> *"동일 파이프라인이 셔틀 정류장에 이식된다. `대기 인원 ÷ 처리율` 구조가 `대기 인원 ÷ 배차 정원`으로 대응된다."*

## 3. 시스템 설계

### 3-1. 출력 — 혼잡도가 아니라 **시간**

```
🟢  "지금 줄 서면 4분"      여유
🟡  "지금 줄 서면 11분"     다음 수업까지 시간 보고 판단
🔴  "지금 줄 서면 23분"     포기하거나 다른 식당으로
```

혼잡도는 **상태**고, 대기시간은 **의사결정 정보**입니다.
학생이 "다음 수업까지 20분인데 23분?" 하고 즉시 계산할 수 있어야 합니다.

### 3-2. 두 개의 동작 모드

무게중심은 **계측 모드**에 둡니다. 예측은 보조입니다.

```
[모드 1 · 예측]  ── 보조 기능
   교시 종료까지 남은 시간 · 요일 · 메뉴 · 날씨 · 시험기간
        → "5분 뒤 도착 시 예상 대기 11분"
   ※ 불확실성이 전부 여기 몰림. 황색 구간이 넓어도 무방

[모드 2 · 계측]  ── ★핵심 기능★
   카메라   : 현재 대기 인원 N명
   빔브레이크: 최근 1분 통과 M명 → 처리율 확정
        → 대기시간 = N ÷ M   (실시간, 예측 아님)
   ※ 책상 위 게이트 모형만으로 100% 증명 가능
```

> **왜 계측이 핵심 기능이어야 하는가**
> *"최종 시연에서 핵심 기능이 동작하지 않으면 프로젝트 점수 상한 70%"*
> 핵심 기능이 예측이면 데이터 부족·설치 지연 등 **팀이 통제할 수 없는 변수에 성적이 걸립니다.**
> 계측은 게이트 모형만으로 증명되므로 **팀이 완전히 통제**합니다.

### 3-3. 노드 구성 — 풀 노드 1 + 경량 노드 1

교내 식당은 3개소(학생회관 · 기숙사 · 교직원)입니다. 전부에 라즈베리파이를 놓으면 예산을 넘습니다.

| 식당 | 구성 | 선정 이유 |
|---|---|---|
| **학생회관** | **풀 노드** — 카메라 + AI + 라즈베리파이 5 + 빔브레이크 | 학생 주력, 인원 최다 → 데이터 밀도 최고. 코너가 여러 개라 **코너별 비교**까지 가능 |
| **기숙사 식당** | **경량 노드** — 빔브레이크 2쌍 + 아두이노 + LED (카메라·AI 없음) | 저녁·주말 패턴이 달라 **모델 일반화 검증**에 유리 |
| **교직원 식당** | **범위 제외** | **대상 사용자(학생)가 아님** — 예산이 아닌 사용자 정의에 따른 제외 |

**경량 노드 동작 원리** (카메라 없이 대기시간 산출)

```
줄 입구 빔브레이크 A ──┐
                       ├→  현재 줄 인원 = (A 누적) − (B 누적)
배식구 빔브레이크 B ──┘    처리율      = B의 최근 1분 카운트
```

- 부품값 약 8만원. 풀 노드에서 학습한 처리율 모델을 그대로 사용
- 누적 차분은 오차가 쌓이므로 **일정 시간 통과가 없으면 0으로 리셋**

### 3-4. 이 구성의 부수 효과 — AI 기여도를 정량 증명

두 노드가 **같은 문제를 다른 방식으로** 풉니다.

| | 풀 노드 | 경량 노드 |
|---|---|---|
| 방식 | 카메라 + AI 검출 | 빔브레이크 차분만 |
| AI | 있음 | **없음 (대조군)** |

학기말에 실측 대비 오차를 비교하면 **"AI 노드 ±1.2분 / 비AI 노드 ±4.5분"** 같은 결과가 나옵니다.

> 심사 단골 질문인 **"AI가 꼭 필요합니까?"** 에 숫자로 답할 수 있습니다.
> 대부분의 팀이 말로만 주장하는 것을 **대조군을 만들어 측정**합니다. 최종 보고서의 핵심 실험 결과.

|---|---|---|

| ② MCU 처리 | ✅ | 아두이노 — 인터럽트 카운팅, 상태 머신, LED·서보 구동, 워치독 |
| ③ AI 판단 | ✅ | 인원 검출 · 처리율 추정 · 도착시점 대기시간 예측 (**레벨 2 온디바이스**) |
| ④ **액추에이터** | ✅ | **입구 신호등 LED + 서보 안내판 + 부저** ← 9/3에 비어 있던 칸 |
| **인터럽트** | ✅ | **배식구 통과 감지** — 통과 0.3초, 폴링으로는 누락. *인터럽트여야만 하는 이유*가 명확 |
| **AI 3초 폴백** | ✅ | AI 무응답 → **빔브레이크 차분으로 전환** → 그것도 실패 → 시간표 기반 + "확인 불가" 표시 |
| **실존 문제 근거** | ⬜ | **오늘 점심 실측 1회 필요** (10절) |
| **기존 제품이 놓친 것** | ✅ | 5절 |

### 폴백 설계 원칙 — 손실이 비대칭입니다

- "금방 먹는다"고 했는데 오래 걸림 → **최악.** 학생이 수업에 늦음
- "오래 걸린다"고 했는데 금방 먹음 → 괜찮음

→ **애매하면 대기시간을 길게 표시**합니다. 통계적으로는 분포의 **보수적 분위수**를 채택합니다.

## 5. 기존 서비스가 놓친 것

대학 식당 혼잡도 앱은 이미 존재하므로, 차별점을 명시해야 합니다.

### ① 기존은 "지금", 우리는 "내가 도착할 때"

공대 건물에서 식당까지 5분 걸립니다. **지금 한산해도 도착하면 붐빕니다.**
점심 피크는 교시 종료 시각(12:00, 12:15)에 파도처럼 몰리기 때문에 5분 차이가 결정적입니다.

> **"5분 뒤 도착 시 예상 대기 11분"** — 이걸 하는 서비스가 없습니다.

예측 입력이 풍부합니다: 교시 종료까지 남은 시간 · 요일 · **오늘 메뉴**(인기 메뉴 날 폭증) · 날씨(비 오면 외부 식당 대신 학식으로 집중) · 시험기간.

### ② 식당 간 · 코너 간 비교

> **"학생회관 12분 / 기숙사 4분"**, **"한식 12분 / 분식 3분"**

기존 앱은 식당 단위 혼잡도만 알려줍니다. 학생이 실제로 필요한 건 **어디로 갈지**입니다.
한 식당 안에 코너가 여러 개면 카메라 1대로 여러 줄을 동시에 보므로, **1개소만으로도 비교 가치가 증명**됩니다.

### ③ 문제 정의의 격상 — 수요 분산

식당이 3개인데 학생이 어디가 덜 붐비는지 모르기 때문에 익숙한 곳으로 몰립니다.
즉 진짜 문제는 "붐빈다"가 아니라 **"수요가 분산되지 않는다"** 입니다.

| | 목적 |
|---|---|
| 초기 구상 | 학생에게 혼잡도를 알려준다 |
| **최종** | **학생의 시간을 아끼고, 학교 전체의 수요를 분산시킨다** |

> 두 번째는 **설치 협조를 요청할 때의 명분**이 됩니다. "학생 편의"보다 "식당 운영 효율"이 결재가 잘 납니다.
> 제안서의 기대효과 항목도 이것으로 채웁니다.

---

## 6. 프라이버시 — 강점으로 전환

식당은 사람이 많이 찍히므로 이 질문이 반드시 나옵니다. 세 가지를 설계에 넣습니다.

1. **카메라를 머리 위에서 아래로** 향하게 설치 → 얼굴이 잡히지 않고 정수리만 보임. 인원 카운트에는 이 각도가 더 정확
2. **영상 비저장** — 인원 수만 기록
3. **온디바이스 처리** — 영상이 네트워크로 나가지 않음

> 3번이 특히 중요합니다. **레벨 2(온디바이스)를 선택한 이유가 프라이버시**라는 기술적 정당화가 되어,
> 레벨 1(클라우드 API)을 쓰지 않은 이유를 설계 원칙으로 설명할 수 있습니다.
> 식당 운영 측 허가를 받을 때도 이 세 줄이 필요합니다.

## 9. 시연 계획

**11월 학술제(SCH E-FESTA)와 최종 시연은 부스에서 진행**되므로, 식당을 가져올 수 없습니다.
이를 미리 설계에 반영합니다.

- **1/N 축소 게이트 모형** — 하드보드지 통로 + 빔브레이크 + LED 신호등.
  관람객이 직접 걸어 지나가면 카운트가 올라가고 신호등이 바뀝니다. **참여형이라 부스에서 가장 잘 통합니다**
- **현장 녹화 영상 리플레이 모드** — 실제 식당에서 찍은 영상을 카메라 입력 대신 흘려보내는 스위치. 실측 데이터로 동작한다는 증거
- **폴백 시연** — 라즈베리파이 전원을 뽑아도 아두이노가 빔브레이크 차분으로 신호등을 계속 구동.
  **가장 확실하게 점수를 받는 장면**
