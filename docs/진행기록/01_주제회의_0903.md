## 3. 구상한 시스템 구성

```
하드웨어(센서)로 사람 수 측정
        ↓
데이터 누적 (요일 × 시간대)
        ↓
AI: "○요일 ○시의 혼잡도는 이 정도" 패턴 학습 · 예측
        ↓
앱으로 학생들에게 표시
```

- **테스트 장소**: 학교 멀티 / 연구실
  → 실제 식당·정류장에 설치하지 못해도 **프로토타입 검증은 실내에서 가능**

## 4. 요건 대비 점검 — 현재 2칸이 비어 있음

| 요건 | 현재 |
|---|---|
| ① 센서 입력 | ✅ 있음 |
| ② MCU 처리 | ✅ 있음 |
| ③ AI 판단 | ✅ 요일 · 시간대 패턴 학습 — 그대로 사용 가능 |
| ④ **액추에이터** | ❌ **앱 · 화면만으로는 미충족** |
| **인터럽트 1곳 이상** | ❌ 미정 |
| **AI 3초 무응답 시 폴백** | ❌ 미정 |

> ⚠️ **"앱만 있는 프로젝트"는 명시된 반려 유형.**
> 앱은 유지하되, **물리적으로 움직이거나 켜지는 장치**가 현장에 하나는 있어야 함.

### 빈칸을 채우는 안

- **액추에이터** — 정류장/식당 입구의 **탑승·입장 커트라인 LED 스트립** + **회전 안내사인(서보)** + 음성 안내
- **인터럽트** — **입구 IR 빔브레이크 통과 카운트**
  (사람이 0.3초 만에 통과 → 폴링으로는 놓침. *인터럽트여야만 하는 이유*가 명확해 심사에서 설명하기 좋음)
- **폴백** — AI 무응답 시 빔브레이크 단순 카운트로 전환 → 그것도 실패 시 시간표 기반 안내 + "혼잡도 확인 불가" 표시
  (**애매하면 절대 "이용 가능"을 띄우지 않는다** — fail-safe 방향을 명시)

## 5. 차별점 후보 — "혼잡도"가 아니라 "내가 탈 수 있느냐"

기존 서비스(카카오맵 · 경기버스 혼잡도)는 **차내가 얼마나 찼는지**만 알려줌.
실제 고통은 **"기다렸는데 내 앞에서 줄이 끊기는 것"**.

→ **차내 잔여 정원 × 현재 대기 인원 × 내 순번**을 결합해야 *"당신은 이번 차에 못 탑니다"* 를 말할 수 있고,
이걸 하는 제품이 없음. **"기존 제품이 놓친 것 하나"** 요건에 대한 답으로 사용 가능.

참고: 셔틀은 출발 정류장에서 태우고 중간 하차가 적으므로,
**출발지 정류장에서 승차 인원만 세면 차내 인원이 확정** → 버스 차량에 장비를 달지 않아도 됨(허가 · 보험 문제 회피).
