# 혼잡도 판단 방식 — 무엇을 어떻게 바꿨나 (2026-10-29)

학생용 화면의 "지금 가면 바로 앉을 수 있어요 / 지금 가도 앉을 수 있어요 / 지금은 자리 찾기가 어려워요"(여유 · 보통 · 혼잡)를 정하는 방법이 두 번 바뀌었습니다. 이 문서는 바뀐 이유, 지금 쓰는 계산식, 코드 위치, 실제 기록으로 비교한 결과를 정리합니다.

계산식의 근거는 팀원이 정리한 [혼잡도-계산.md](../혼잡도-계산.md)입니다.

## 한눈에 보기

| 기간 | 방식 | 계산 | 문제점 |
|---|---|---|---|
| ~10/28 | **좌석 대비 인원** | `빈자리 비율 = (좌석 수 − 인원) / 좌석 수` | 4인석에 2명만 앉아도 남은 2석은 실제로 안 쓰임. 사람 수가 좌석의 70%만 돼도 체감은 꽉 참 |
| 10/28 ~ 10/29 오후 | **빈 테이블 비율** | `빈 테이블 수 / 전체 테이블 수` | 2인석과 6인석을 같은 1개로 셈. 서 있는 사람(곧 앉을 사람)은 반영 안 됨 |
| **10/29 저녁 ~ (지금)** | **점유 테이블 좌석 + 전체 인원** | `사용 좌석 = max(점유 테이블 좌석 합, 전체 인원)` → `남은 좌석 비율 = (전체 좌석 − 사용 좌석) / 전체 좌석` | — |

단계 기준은 세 방식 모두 같습니다: **남은 비율 30% 이상 여유 · 10~30% 보통 · 10% 미만 혼잡**.

## 지금 계산식

```
S_total = 전체 좌석 수 (등록한 테이블 51곳의 좌석 합, 150석)
S_occ   = 점유 테이블의 좌석 합 (사용 중 + 자리 비움 테이블)
P       = 식당 안 전체 인원 (좌석 카메라 cam1~3 합계, 키오스크 cam4 제외)

사용 좌석  = max(S_occ, P)
남은 비율  = (S_total − 사용 좌석) / S_total   → 여유 / 보통 / 혼잡
```

왜 `max`인가:
- **점유 테이블은 통째로 쓴다고 본다.** 학생식당에서는 모르는 사람과 합석을 잘 안 하므로, 4인석에 1명이 앉아도 4석이 찬 것으로 본다 → `S_occ`
- **서 있는 사람도 곧 앉을 수요다.** 배식을 받고 자리를 찾는 사람이 많아 `P`가 `S_occ`보다 크면, 그만큼 자리가 더 필요하다 → `P`
- 두 값 중 큰 쪽이 실제로 필요한 좌석의 **하한**이다. 그래서 판단이 보수적인 쪽(헛걸음을 막는 쪽)으로 틀린다.
- **자리 비움**(잠깐 자리를 떠난 테이블)도 점유로 센다. 가방을 두고 간 자리일 수 있기 때문이다.

참고로 서버는 빈 좌석을 범위로도 계산한다: `[보수 = S_total − max(S_occ, P), 낙관 = S_total − max(점유 테이블 수, P)]`. 낙관 값은 합석을 허용했을 때다. 화면에는 지금 "빈 테이블 ○개"만 보여주고 이 범위는 표시하지 않는다.

## 실제 기록으로 비교 (2026-10-29, 08:00~19:30)

서버 DB의 테이블 상태 기록과 인원 기록을 10분 단위로 맞춰, 바꾸기 직전 방식(빈 테이블 비율)과 지금 방식을 같은 데이터에 적용했습니다.

| 시각 | 빈 테이블 | 빈 좌석 | 인원 P | 빈 테이블 비율 → 단계 | 지금 방식 → 단계 |
|---|---|---|---|---|---|
| 11:20 | 16.3 | 38 | 42 | 32% 여유 | 25% **보통** |
| 11:50 | 1.3 | 2 | 86 | 3% 혼잡 | 1% 혼잡 |
| 12:00 | 0.4 | 1 | 95 | 1% 혼잡 | 1% 혼잡 |
| 12:30 | 11.4 | 28 | 69 | 22% 보통 | 19% 보통 |
| 13:10 | 16.5 | 35 | 46 | 32% 여유 | 23% **보통** |
| 13:20 | 17.3 | 42 | 34 | 34% 여유 | 28% **보통** |
| 14:00 | 16.3 | 41 | 40 | 32% 여유 | 27% **보통** |

- 10분 칸 63개 중 **4개만 단계가 달라졌고**, 모두 "여유 → 보통"으로 한 단계 보수적이 됐다. 4·6인석 같은 큰 테이블이 먼저 차서, 테이블 개수보다 좌석으로 볼 때 더 붐비기 때문이다.
- 점심 피크(11:50~12:20)는 두 방식 모두 혼잡.
- `P`가 `S_occ`보다 컸던 칸은 63개 중 4개(아침, 테이블이 거의 비어 있을 때)뿐이었다. 오늘은 `P` 쪽이 판단을 바꾼 적이 없지만, 배식 줄이 길게 서는 날에는 안전장치 역할을 한다.
- 12:00처럼 테이블이 다 찼는데 인원은 95명(좌석 150석)인 경우가 문서의 "4인석에 1~2명씩" 상황이다. 사람 수만 보면 37% 여유로 나오지만 실제로는 앉을 테이블이 없다. 지금 방식은 이를 혼잡으로 판단한다.

## 받아들이지 않았거나 나중으로 미룬 것

| 문서의 제안 | 결정 | 이유 |
|---|---|---|
| 웹에 "빈 자리 {보수}~{낙관}석" 범위 표시 | 보류 | 화면을 단순하게 하려고 "빈 좌석 약 ○석" 문구를 뺀 상태. 서버 응답(`free_seat_range`)에는 넣어 둠 |
| 남은 비율이 0 미만이면 "만석" 단계 | 보류 | 오늘 기록에서는 한 번도 나오지 않음. 지금은 혼잡에 포함 |
| `P`를 1~2분 이동평균으로 평활화 | 일부 반영되어 있음 | 라즈베리파이가 이미 카메라별로 최근 15초 75퍼센타일로 보정함 |
| 단계 전환에 히스테리시스 (예: 혼잡 진입 10%, 복귀 15%) | 남은 일 | 경계 근처에서 단계가 깜빡이는지 며칠 지켜본 뒤 결정 |
| 긴 테이블을 4인 구간으로 쪼개 등록 | 해당 적음 | 가장 큰 테이블이 6인석(T38, T42) |

## 한계

- `P`에는 지나가는 사람, 배식대 앞 줄, 식사를 마치고 나가는 사람도 섞여 있어 수요를 조금 크게 본다.
- 테이블 판정은 "영역 안에 사람이 있는가"만 본다. 영역을 스치는 사람 때문에 잠깐 점유로 보일 수 있다 (10/29 자리 비움 오탐 수정으로 일부 완화).
- 기준(30% · 10%)은 아직 현장 관찰로 보정하지 않았다. 점심시간에 "빈 테이블을 쉽게 찾음 / 어려움 / 못 찾음"을 기록해 맞추는 것이 다음 단계다.
